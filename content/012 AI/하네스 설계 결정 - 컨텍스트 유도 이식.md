# 하네스 설계 결정: 가이드 vs 차단형 하네스, 그리고 컨텍스트 유도 이식

> **상태**: 결정됨 (2026-05-27)
> **결정 요지**: 현 단계에서는 [[AI와 TDD+BDD 하기 - Low Tech Dept V5]]를 주 방법론으로 유지하고, [[Context blocking Harness V2]]의 핵심 아이디어 **단 하나 — "컨텍스트를 코드 그래프에서 유도" — 만** 점진적으로 이식한다. 강한 차단(샌드박스·디스크 분리)은 보류한다.

## 1. 배경

이 문서는 "더 나은 LLM 코딩 하네스"를 만들기 위한 과정의 의사결정 기록이다. 두 산출물이 **경쟁이자 협력** 관계에 있다.

- [[AI와 TDD+BDD 하기 - Low Tech Dept V5]] — 지금 쓰는 방법론(prose + 템플릿). 어떤 AI 도구로도 오늘 바로 동작.
- [[Context blocking Harness V2]] — 컨텍스트 차단형 MCP 하네스 기획안(아직 미구현).

## 2. 기존 가이드의 통점 (출발점)

| # | 통점 | 체감 |
|---|---|---|
| ① | 코드 하나 작성에 수반되는 **문서가 많다** | spec/invariant/interface/test + 링크 블록 유지 부담 |
| ② | 기능 구현에 **필요한 컨텍스트가 불명확** → 토큰 오버헤드 | 안전하게 과하게 읽거나, 덜 읽고 왕복 |

### 통점의 근원 분해

가이드의 "문서"는 성격이 다른 두 종류가 섞여 있다.

| 종류 | 예 | 성격 | 줄일 수 있나 |
|---|---|---|---|
| **의도/계약** | spec, invariant, interface, test | 코드가 *무엇을* 해야 하는지. 사고 그 자체 | ❌ (본질) |
| **컨텍스트 경계** | 링크 블록, "무엇을 읽어야 하나" | 구현하려고 *알아야 하는* 범위 | ✅ 코드 그래프에서 유도 가능 |

- 통점 ① = 의도 문서를 작은 작업에도 과적용(규모 판단 미사용) + 컨텍스트 경계를 **손으로** 관리하는 부기 노동.
- 통점 ② = 컨텍스트 경계가 정밀하지 않아서.

**결론: 두 통점 모두 뿌리는 ②(컨텍스트 경계)다.**

## 3. 핵심 발견: 둘은 다른 층위다

- 가이드는 *"무엇을 생각하고 무엇을 만들 것인가"*(contract-first, 행동적 slicing, 검증)에 답하는 **방법론**이다.
- 하네스는 *"컨텍스트를 어떻게 기계적으로 한정/강제하나"*에 답하는 **도구**다.

하네스를 완성해도 그 위에서 결국 가이드 같은 방법론이 돌아야 한다(무슨 계약을 쓸지, 어떻게 행동 단위로 쪼갤지는 도구가 정해주지 않음). **따라서 하네스는 가이드를 대체하는 경쟁자가 아니라, 가이드의 일부를 자동화/강제하는 도구다.**

## 4. 하네스 V2 평가 요약

### 강점
- **통합 통찰**: 유지보수성·토큰·조립성 세 규칙이 "contract로 정의된 vertical slice"라는 단일 단위로 동시에 풀린다.
- **"권한 상승 = 차단 해제가 아니라 경계 재정의"** 원칙 (Refactor/Debug 모드 설계).
- **Roslyn 선택**이 기술적으로 단단(SymbolFinder/SemanticModel/CallHierarchy로 owns/depends_on/impact가 한 API).
- 어댑터로 tool-specific hook 격리, 규칙 lazy 로딩.

### 약점 / 토대 리스크
- **강한 차단의 실현 가능성이 주장보다 약하다.** "MCP 권위만으로 차단 성립"은 틀림 — 에이전트의 네이티브 Read/Bash를 막으려면 결국 **OS 샌드박스**가 필요(= agent-agnostic일 뿐 environment-agnostic 아님).
- **소스를 디스크에서 들어내면 쓰기·빌드·테스트가 깨진다.** 쓰기 경로가 기획서에 비어 있음. Unity/Roslyn 테스트는 디스크 소스를 요구.
- **"vertical slice"가 행동 단위 → 심볼 집합으로 조용히 재정의**됨(검증 가능성 본질 소실).
- "실측 최대 절감"은 데이터 없는 단언. 시그니처-only는 contract가 풍부할 때만 성립(레거시엔 그게 없음).
- Debug=스택 트레이스 기반은 *throw되는 쉬운 버그*만 커버.
- `forbidden` 목록 ↔ "경계 밖은 안 보임"의 내부 모순(안 보이면 forbidden이 왜 필요?).

## 5. 결정

1. **as-is(둘 다 미수정) 기준으로는 가이드가 우위.** 가이드는 오늘 동작하는 완결된 방법론이고, 하네스는 토대 리스크를 안은 미구현 기획서이며, 애초에 같은 범주가 아니다.
2. **하네스에서 단 하나 — 컨텍스트 유도 — 만 떼어 가이드에 이식한다.** 이것이 통점 ②(그리고 ①의 절반)의 정공법이다.
3. **강한 차단은 보류한다.** 토큰 절감은 *유도*만으로 달성되며, 물리적 차단은 *강제*(규율) 문제를 푼다. 현재 통점은 토큰·문서지 강제가 아니므로, 비싸고 불안정한 절반은 짓지 않는다.

> 핵심 분리: **유도 = 싸고 통점을 직접 해결 / 강한 차단 = 비싸고 다른 문제를 해결.**

## 6. 합성안 — 각자에서 가져올 것

| 요소 | 출처 | 이유 |
|---|---|---|
| 의도/계약을 사람이 소유 (spec/invar/interface/test) | 가이드 | 도구가 의도를 만들지 못함 |
| 규모 적응성 (Micro→Large) | 가이드 | 통점 ①의 정답. 작은 작업엔 경량 경로 |
| 행동적 vertical slice (검증 가능 단위) | 가이드 | 심볼 집합 환원은 본질 소실 |
| **컨텍스트 자동 유도 (owns 전문 + deps 시그니처)** | 하네스 | 통점 ②의 정답. 토큰 절감 핵심 |
| 규칙 lazy 로딩 | 하네스 | harness 자체 토큰 절감 |
| 3-mode (Build/Refactor/Debug) | 하네스 | 실무 비율 반영 (후순위) |
| 물리적 강한 차단 | (보류) | 현재 통점 아님 |

**한 줄 원칙**: *사람은 의도 경계(owns)를 선언하고, 도구는 기계적 경계(deps/impact)를 유도한다. 의도 문서는 규모에 따라 가볍게, 컨텍스트 부기는 전부 도구로.*

## 7. 컨텍스트 유도가 기술적으로 요구하는 것

| # | 조각 | C#/Roslyn 대응 | 난이도 |
|---|---|---|---|
| 1 | 심볼 해석: owns("A.B")를 코드 위치로 매핑 | `MSBuildWorkspace` + `SymbolFinder` | 낮음 |
| 2 | 순방향 의존 추출: owns가 호출하는 것 → deps (규칙 3) | `SemanticModel.GetSymbolInfo` + 구문 순회 | 중간 |
| 3 | 역방향 영향 추출: owns를 누가 호출하나 → impact (규칙 1) | `SymbolFinder.FindReferencesAsync` | 낮음 |
| 4 | 시그니처-only 렌더링 (본문 없이) | `ISymbol.ToDisplayString()` + `GetDocumentationCommentXml()` | 낮음 |
| 5 | 패키징: owns 전문 + deps 시그니처 번들 | 마크다운/JSON 생성 | 낮음 |

Roslyn이 1·3·4를 거의 공짜로 준다. 실제 작업은 2(순방향)와 5(패키징).

## 8. 롤아웃 (싸게 → 강하게)

| Stage | 내용 | 비용 |
|---|---|---|
| **0** | spec.md에 `## Context (읽어도 되는 범위)` 수동 섹션. 세션은 그것만 로드. 가설 검증. | 무료 (가이드 문장) |
| **1** | `owns` 입력 → deps 시그니처 출력 스크립트. OmniSharp(C# LSP)로도 70% 가능. | 며칠 |
| **2** | `mcp__contractfirst__derive_context(owns)` MCP 도구. = 하네스 `enter_slice` − 차단. | 1~2주급 |
| **3** | `impact_of`(역참조) 노출. 규칙 1 검증 + Refactor 수집 재사용. | 추가 |

검증 루프: `session.log`에 **miss**(번들에 없어 추가로 읽음=유도가 좁음) / **waste**(번들에 넣었는데 안 씀=넓음)를 기록해 deps 깊이(1-hop/2-hop)를 튜닝.

## 9. 기존 contractfirst 툴링과의 관계

현재 `contractfirst` MCP는 **전부 문서/계약 층**에서만 작동한다: `verify_links`(Links 상호참조 검증), `run_verify`, `score_ambiguity`, `track_manual_checks`, `analyze_verify_failure`. **코드 그래프를 보는 도구는 없다** — 컨텍스트 유도는 빠진 "코드 층"이다.

역설적 기회: `verify_links`가 검사하는 수동 `## Links` 블록이 곧 통점 ①의 부기 노동이다. **유도를 넣으면 그 수동 관리를 도구가 대신하므로, 추가가 아니라 일부를 삭제하게 된다.** `derive_context`는 `verify_links` 옆에 자연스럽게 슬롯인된다.

## 10. 미해결 결정사항

- **granularity**: 파일 단위(싸다, OmniSharp/grep) vs 심볼 단위(정밀, 토큰 win 큼, Roslyn). → 심볼 단위가 절감 핵심.
- **유도 컨텍스트의 거처**: slice 디렉토리의 생성 파일(git 가시·검토 가능) vs 휘발성 MCP 응답.
- **시작 방식**: 수동 우선(Stage 0) vs 바로 Roslyn.
- **deps 깊이**: 1-hop 기본, miss 빈발 시 2-hop?
