# 컴파일 강제형 Slice Harness 기획안 (v3)

> 빌드 경계 강제형 · **컴파일러가 강제** · tool-agnostic · greenfield Unity/C# 우선

## 위치: 선배들과의 관계

이 기획안은 [[AI와 TDD+BDD 하기 - Low Tech Dept V5]](가이드)도, [[Context blocking Harness V2]](차단형)도 아닌 **제3의 강제 방식**이다. 차이는 단 하나 — **강제의 위치(enforcement locus)**다.

|접근|강제 위치|성격|
|---|---|---|
|가이드 (V5)|사람의 규율 (프롬프트·리뷰)|약함, 협상 가능|
|차단형 (V2)|읽기 시점 비가시성 (MCP firewall)|강하지만 툴체인과 마찰 (샌드박스·쓰기경로)|
|**컴파일 강제형 (V3)**|**컴파일/빌드 시점 불가능성**|강하고 툴체인과 *협력*|

배경 의사결정은 [[하네스 설계 결정 - 컨텍스트 유도 이식]] 참고.

## 핵심 명제

> **경계를 숨기지 않는다. 경계를 넘는 코드가 *컴파일되지 않게* 만든다.**

기존 두 접근은 "컨텍스트가 많다"는 **증상**을 다룬다(규율로 자제시키거나, 읽기를 숨기거나). 그러나 코드를 숨겨도 코드는 여전히 엉켜 있고, LLM은 엉킨 코드 위에서 눈 가린 채 작업한다. V3는 **원인**을 친다: 코드를 물리적으로 모듈화해 *볼 게 애초에 적게* 만든다. 강제 주체는 커스텀 firewall이 아니라 **개발자가 이미 돌리는 컴파일러/빌드 시스템**이다.

## 1. 배경과 목표

LLM 코딩에서 다음 세 규칙을 **시스템적으로 강제**한다.

|#|규칙|의미|
|---|---|---|
|1|유지·보수성|기능 한 개 구현 시 영향받는 다른 코드를 최소화|
|2|토큰 최적화|기능을 vertical slice로 쪼개 slice마다 한 세션 → 누적 토큰 절감|
|3|조립식 코드|특정 기능 구현에 알아야 하는 컨텍스트 양을 최소화|

### 핵심 통찰

세 규칙은 전부 **"의존성 구조"** 하나의 문제로 환원된다. 한 기능이 코드베이스의 작고 경계 분명한 영역만 건드리게 만들면 셋이 동시에 풀린다. 따라서 harness의 본질은 *읽기를 막는 게이트키퍼*가 아니라 **경계를 컴파일러가 강제하는 모듈 구조 + 그 빌드 그래프를 읽어 컨텍스트를 패키징하는 얇은 도구**다.

## 2. 설계 결정

|항목|결정|
|---|---|
|대상 스택|Unity/C# 우선. 경계 = Assembly Definition(`.asmdef`)|
|경계 정의 주체|AI 제안 → 사람 승인. 경계는 `.asmdef` 파일로 남음(빌드 산출물 겸함)|
|강제 수준|**C# 컴파일러가 강제** (위반 = 빌드 실패)|
|도구 종속성|tool-agnostic. 강제가 컴파일러에 있으므로 어떤 에이전트·CI·사람이든 동일하게 막힘|
|적용 범위|**greenfield 우선** — Day 1부터 경계를 설계(레거시 retrofit은 별도 on-ramp)|

언어-일반 대응물: Bazel/Nx target `deps`, Rust crate+`pub`, Java Module, .NET `internal`+프로젝트 참조. 원리 동일.

## 3. 강제 메커니즘: 컴파일 불가능성

Unity `.asmdef`가 그대로 이 메커니즘이다. 새 도구가 **필요 없다.**

- **slice = 하나의 asmdef** (독립 컴파일 단위)
- 기본 `internal` 가시성 → 어셈블리 밖에서 내부 타입은 **보이지도 참조되지도 않음**
- 어셈블리 참조는 **순환 금지** (Unity가 컴파일 에러로 강제) → 그래프가 자동 DAG
- 참조 어셈블리는 **컴파일된 메타데이터로** 본다(소스 아님) → "시그니처만"이 **공짜**로 성립
- 참조 안 한 어셈블리의 타입을 쓰면 → **컴파일 실패**. dep 추가는 `.asmdef`를 고치는 명시적·리뷰 가능한 행위

### firewall vs compiler

|차단형(V2)|컴파일 강제형(V3)|
|---|---|
|소스를 디스크에서 들어내야 함|소스는 그대로, 경계만 컴파일러가 지킴|
|쓰기 경로를 MCP로 재구현|네이티브 Edit/Write 그대로|
|빌드·테스트와 마찰|빌드·테스트가 곧 강제 기제|
|MCP만 지원하면 강함(but 샌드박스 필요)|컴파일러를 돌리면 누구나 막힘|

## 4. 전체 아키텍처

```
의존 선언(.asmdef)  →  빌드 그래프(권위)  →  컨텍스트 서버(얇음)
   [단일 진실원천]        [컴파일러가 강제]        [읽고 패키징만]
```

### 단일 선언이 3역을 한다

차단형이 `slice.yaml` + 링크 블록 + 컨텍스트 매니페스트를 따로 유지했던 것과 달리, **`.asmdef`의 의존 선언 하나가:**

1. **빌드 계약** (컴파일러가 강제)
2. **컨텍스트 매니페스트** (세션에 무엇을 로드할지)
3. **blast-radius 인덱스** (역의존 = 영향 범위)

세 역할을 동시에. 개발자가 *어차피 빌드를 위해 써야 하는* 단 하나의 선언이다 → 가이드의 통점 ①("문서가 너무 많다")을 근본에서 제거(유지할 별도 문서 없음).

## 5. 산출물 구조

slice 하나 = 디렉토리 하나 = asmdef 하나.

```
/Assets/Slices/Inventory.QualityGrade/
  Inventory.QualityGrade.asmdef      ← 경계 정의 (사람 승인 핵심 파일)
  IQualityGradeService.cs            ← 공개 API = 인터페이스 계약 (public)
  QualityGradeService.cs             ← 구현 (internal)
  Tests/
    Inventory.QualityGrade.Tests.asmdef
    QualityGradeServiceTests.cs
```

- 공개 표면(`public`)이 곧 [[AI와 TDD+BDD 하기 - Low Tech Dept V5]]의 *인터페이스 계약*. 사람이 소유.
- 구현은 `internal` → 다른 slice가 *물리적으로* 못 봄.

### asmdef 예시

```json
{
  "name": "Inventory.QualityGrade",
  "references": [
    "Item.Database",
    "Player.Stats"
  ],
  "autoReferenced": false
}
```

- `references` = depends_on. 여기 없는 어셈블리는 참조 불가 = 컴파일 실패.
- `SaveSystem`이 목록에 없으면 → V2의 `forbidden`을 명시적으로 적을 필요조차 없다. *애초에 못 부른다.*

## 6. 세 목표가 구조적으로 강제되는 방식

|목표|강제 메커니즘|왜 자동인가|
|---|---|---|
|1. 영향 최소|빌드 그래프 역의존 = 정확한 blast radius. internal은 어셈블리 밖에서 안 보여 숨은 결합 *불가*|A의 internal 변경은 공개 API를 안 건드리면 B에 영향 0 — 컴파일러 보장|
|2. 토큰|작업 = 한 어셈블리 source + 참조 어셈블리 메타데이터(공개 시그니처)|참조는 메타데이터로 봄 → 시그니처만 공짜. 어셈블리 1개 = 세션 1개|
|3. 최소 컨텍스트|참조 안 한 타입은 컴파일 실패. dep 추가는 명시적 선언|컨텍스트 확장 = 의존 선언 = 경계 위반의 가시적 기록|

## 7. 운영 모드: Build / Refactor / Debug

권한 상승 원칙은 V2와 동일: **"차단 해제가 아니라 경계 재정의."** 단 V3에선 경계 = 참조 그래프의 부분집합이고, 확장해도 여전히 컴파일러가 DAG를 강제한다.

|모드|경계 결정|메커니즘|
|---|---|---|
|Build|단일 asmdef|한 어셈블리 안에서 작업. 참조 어셈블리는 공개 표면만 로드|
|Refactor|공개 API 변경의 역의존 집합|`blast_radius`(역참조)가 곧 refactor manifest. *빌드 그래프가 자동 산출*|
|Debug|스택 트레이스에 등장한 어셈블리들|트레이스의 타입 → 소속 어셈블리 역추적 → 임시로 함께 로드. 세션 후 폐기|

Refactor의 핵심 이점: V2는 `impact_of`를 별도 계산해야 했지만, V3는 **공개 시그니처를 바꾸면 컴파일러가 깨지는 모든 호출처를 정확히 알려준다** — 영향 범위가 추정이 아니라 *컴파일 결과*다.

## 8. 도구: 얇은 빌드-그래프 컨텍스트 서버

강제는 컴파일러가 하므로 도구는 firewall이 아니라 **내비게이터**다. 전부 표준 MCP.

|도구|역할|
|---|---|
|`context(slice)`|내 어셈블리 source 전문 + 참조 어셈블리들의 **공개 표면만** 패키징 (Roslyn `MetadataReference`로 본문 없이 렌더링). 규칙 .md도 lazy 동봉|
|`blast_radius(symbol)`|역참조 질의 — 이 공개 API를 누가 쓰나 (규칙 1 + refactor 수집)|
|`propose_boundary(symbols)`|응집도/참조 분석으로 asmdef 분할 초안 (사람 승인 대기)|
|`check_cycle()`|제안된 참조가 순환을 만드는지 사전 경고 (컴파일러보다 빠른 피드백)|

> 도구가 죽어도, 잘못 써도 **강제는 유지된다** — 컴파일러가 최후의 보루. 도구는 *편의*지 *강제 주체*가 아니다. 이것이 V2 대비 견고성의 근원.

## 9. 토큰 최적화 정리

|레버|방법|효과|
|---|---|---|
|규칙 .md 상주 최소화|루트 + 나머지 MCP lazy 반환|harness 자체 토큰 절감|
|참조는 메타데이터로|컴파일러 기본 동작 — 본문 대신 공개 시그니처|**구조적 공짜**(별도 추출 로직 불필요)|
|slice = 어셈블리 = 세션|어셈블리마다 새 세션|누적 토큰 차단|
|경계 위반 불가|컴파일러가 막아 컨텍스트 누수 차단|over-read가 *발생 못 함*|

## 10. C#/Roslyn/Unity 구현 노트

- **공개 표면 렌더링**: Roslyn `MetadataReference`/`PEReference`로 참조 어셈블리를 열면 소스 없이 public 멤버의 시그니처를 `ISymbol.ToDisplayString()` + XML doc(`GetDocumentationCommentXml()`)으로 렌더 — V3 컨텍스트 패키징의 핵심.
- **빌드 그래프 파싱**: `.asmdef`(JSON)의 `references`가 곧 그래프. 별도 그래프 유지 불필요.
- **Unity 동기화와 협력**: V2는 Roslyn 워크스페이스가 Unity의 `.csproj` 재생성과 충돌했지만, V3 도구는 *강제가 아니라 조회*만 하므로 충돌해도 컴파일러 강제는 멀쩡하다. 에디터 OFF는 `Csc` 응답 파일, ON은 파일와처 증분 — V2와 동일하되 실패 시 영향이 작다.

## 11. 그린필드 셋업 (Day 1)

신규 프로젝트이므로 **첫날부터 경계를 깐다** — 비용이 가장 싼 시점.

1. **루트 규약**: `/Assets/Slices/<도메인>.<기능>/` 디렉토리당 asmdef 하나. `autoReferenced: false`로 암묵 참조 차단.
2. **공개 표면 최소화**: 기본 `internal`. slice 밖에 노출할 것만 `public` 인터페이스로. 이게 인터페이스 계약(사람 소유).
3. **어셈블리 분할 기준** = 가이드의 slice 크기 기준 재사용: "실행해서 확인 가능 / AC 3~7개 / 4~8시간"이면 어셈블리 하나. 더 작으면 합치고, 더 크면 쪼갠다.
4. **횡단 관심사**: 로깅·SaveSystem·이벤트버스 등은 저수준 **공유 어셈블리**(`Core.*`)로 빼고 모두가 참조 가능하게 — 단 이들은 *다른 slice를 참조하지 않는* 리프 노드여야 DAG 유지.
5. **테스트 어셈블리**: slice마다 `*.Tests.asmdef` 동봉. 순수 로직은 EditMode 테스트로.

## 12. 트레이드오프 / 미해결

- **코드가 실제로 모듈화돼야 한다.** 위반을 숨기는 게 아니라 컴파일 불가로 만드니, 설계 규율이 앞단으로 이동(greenfield라 비용은 낮음).
- **순환 금지가 강제된다.** 비순환 설계 강요(목표 1의 핵심)지만 도메인이 본질적으로 엉키면 아플 수 있음 → 인터페이스 분리/이벤트로 끊기.
- **granularity 딜레마**: 어셈블리 과다 → 컴파일 오버헤드+의식 과다 / 과소 → 경계가 컨텍스트를 못 좁힘. 분할 기준(11-3)으로 관리.
- **어셈블리 컴파일 시간**: Unity는 asmdef가 많아지면 도메인 리로드/컴파일 비용 증가 — 측정 필요.
- **미해결**: (a) 공개 표면이 큰 어셈블리는 여전히 컨텍스트가 큼 → 어셈블리 내부에서 더 좁힐 장치 필요? (b) Debug 모드의 동적 경계(런타임 계측)는 향후. (c) 멀티 언어 일반화.

## 13. 다음 단계 (구현 우선순위)

|순위|작업|이유|
|---|---|---|
|1|그린필드 asmdef 규약 + 디렉토리 템플릿 확정 (§11)|강제는 이미 컴파일러에 있음 — 규약만 정하면 *오늘* 강제가 작동|
|2|`context(slice)` 도구 (Roslyn `MetadataReference` 공개표면 렌더)|토큰 절감의 실현 지점. 컨텍스트 패키징 검증|

|4|규칙 .md lazy 반환 + 세션 격리 워크플로우 문서|운영 절차 확정|
|5|asmdef 컴파일 비용 실측 → granularity 가이드라인|11-3 기준을 데이터로 보정|

> **V2 대비 결정적 차이**: 순위 1이 끝나는 순간(규약 확정) **강제가 즉시 성립한다.** 도구(순위 2~)는 편의일 뿐 강제의 전제가 아니다. 차단형이 "MCP 서버가 owns/depends_on을 구분 반환할 수 있느냐"라는 큰 리스크를 1순위에 안고 시작한 것과 정반대다.
