# Understanding the Relationship Between Nginx and Gunicorn in Your Flask Application

The relationship between Nginx and Gunicorn is a classic web server architecture pattern that provides several benefits. Let me explain how they work together in your application:

## Basic Roles

1. Nginx: A high-performance web server and reverse proxy

2. Gunicorn: A WSGI HTTP server that runs your Python/Flask application

3. Flask: Your Python web framework that handles the actual application logic

## How They Work Together

> Client Request → Nginx (port 3000) → Gunicorn (port 2001) → Flask Application

In your setup:

1. Client makes a request to http://beps.hanmaceng.co.kr:13000/memo

2. This request reaches port 13000 on your host, which is mapped to port 3000 on your VM

3. Nginx is listening on port 3000 and receives the request

4. Nginx acts as a reverse proxy - it forwards the request to the appropriate backend server based on its configuration

5. Your Nginx configuration contains rules like:
    
    nginx
    
    Apply to contents_rou...
    
       location /memo/ {
    
           proxy_pass http://127.0.0.1:2001;
    
       }
    

6. This rule tells Nginx to forward requests for /memo/ to Gunicorn running on port 2001

7. Gunicorn receives the request and passes it to your Flask application

8. Your Flask app processes the request using the matching route in your blueprint

9. The response follows the reverse path back to the client

## Why Use This Architecture?

1. Security: Nginx acts as a buffer between the internet and your application server

2. Performance:

- Nginx excels at serving static files and handling multiple connections

- Gunicorn manages Python processes efficiently

1. Reliability: Nginx can handle slow clients without tying up Python processes

2. Flexibility: You can have multiple backend applications behind a single Nginx server

## How Gunicorn Runs Your Flask App

Gunicorn creates worker processes to handle requests. Each worker is a separate Python process that loads your Flask application. In your case, it's running with 4 workers:

text

Apply to contents_rou...

gunicorn -w 4 -b 0.0.0.0:2001 app:app

- -w 4: Run 4 worker processes

- -b 0.0.0.0:2001: Bind to all interfaces on port 2001

- app:app: Load the Flask application named app from the module app.py

## Automatic Startup

The automatic startup is typically managed by systemd, which is Linux's init system. There's likely a systemd service file that starts Gunicorn when the VM boots. It would be located at /etc/systemd/system/flask_app.service or similar.

## Path Translation

One important detail is how paths are translated. When Nginx forwards a request, it can either:

1. Forward the complete path:
    
    nginx
    
    Apply to contents_rou...
    
       location /memo/ {
    
           proxy_pass http://127.0.0.1:2001;
    
       }
    

A request to /memo/123 becomes http://127.0.0.1:2001/memo/123

1. Strip the prefix:
    
    nginx
    
    Apply to contents_rou...
    
       location /memo/ {
    
           proxy_pass http://127.0.0.1:2001/;
    
       }
    

A request to /memo/123 becomes http://127.0.0.1:2001/123

This distinction is important for matching your Flask routes correctly.
