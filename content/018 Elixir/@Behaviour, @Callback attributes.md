# Elixir 비헤이비어와 콜백: 의도된 유연성과 런타임의 중요성 (feat. OOP 언어와의 비교)

Elixir 개발을 하다 보면 `GenServer`나 `Phoenix.LiveView`와 같은 **비헤이비어(Behaviour)**를 접하게 됩니다. 이들은 `mount/2`, `render/1`, `handle_call/3` 등 특정 "콜백(Callback)" 함수를 구현하도록 요구하죠. 그런데 여기서 한 가지 의문이 생길 수 있습니다. `@behaviour` 어트리뷰트는 왜 필요한 걸까요? 그리고 `@callback`으로 선언된 함수가 언제는 필수이고 언제는 선택사항이 되는 걸까요? 마치 다른 OOP(객체 지향 프로그래밍) 언어의 "인터페이스 구현"과 비슷한데, 조금은 모호하게 느껴질 수 있습니다.

이번 블로그 게시물에서는 Elixir 비헤이비어와 콜백의 이러한 "모호함"이 사실은 의도된 설계이며, 그 안에 담긴 철학과 런타임의 중요성을 OOP 언어와의 비교를 통해 파헤쳐 보겠습니다.

## 비헤이비어 (Behaviour)와 콜백 (Callback)의 역할

Elixir에서 **비헤이비어**는 특정 모듈이 따라야 할 **계약(Contract)** 또는 **인터페이스**를 정의하는 방법입니다. 이는 일련의 함수(콜백)를 지정하고, 해당 함수들의 이름, 인자 수(arity), 그리고 타입(Typespec)을 명시합니다.

**콜백**은 비헤이비어에 의해 정의된 계약의 일부로, 특정 시점에 비헤이비어를 구현하는 모듈에 의해 "다시 호출(call back)"될 것으로 예상되는 **특정 함수**를 의미합니다.

- **`@behaviour`**: 모듈이 특정 비헤이비어의 **계약을 따른다**고 컴파일러에 선언하는 어트리뷰트입니다.
    
- **`@callback`**: 비헤이비어를 정의하는 모듈에서, 해당 비헤이비어를 따르는 모듈이 **구현해야 할 함수**의 시그니처를 선언하는 어트리뷰트입니다.
    
- **`@optional_callbacks`**: `@callback`과 유사하지만, 이 비헤이비어를 따르는 모듈이 해당 함수를 **구현하지 않아도 컴파일러 경고를 발생시키지 않는다**는 것을 선언합니다.
    

## OOP 언어 비유: `NotImplementedException`을 던지는 인터페이스 메서드 💥

여러분은 아마 OOP 언어에서 인터페이스를 구현했지만, 특정 메서드의 본문이 단순히 `throw new NotImplementedException();`과 같이 되어 있는 상황을 떠올릴 수 있을 것입니다.

```
// Java 예시
interface MyInterface {
    void requiredMethod();
    void optionalMethod(); // 구현해도 되고 안 해도 되는 개념 (실제 Java에는 명시적인 optional 키워드는 없음)
}

class MyClass implements MyInterface {
    @Override
    public void requiredMethod() {
        // 실제 구현 대신, 아직 구현되지 않았음을 나타내는 예외를 던집니다.
        throw new UnsupportedOperationException("Method not implemented!");
    }

    @Override
    public void optionalMethod() {
        // 이 메서드는 MyClass가 사용되는 특정 상황에서만 필요할 수 있습니다.
        // 구현하지 않거나, 기본 동작만 할 수도 있습니다.
    }
}
```

이 코드는 **컴파일 타임에는 오류가 발생하지 않습니다.** `MyClass`가 `MyInterface`의 계약을 **형식적으로는** 지켰기 때문입니다. 하지만 `requiredMethod()`가 호출되는 **런타임 시점에는 예외가 발생하며 프로그램이 크래시될 것입니다.** `optionalMethod()`는 호출되지 않으면 문제가 없습니다.

## Elixir의 의도된 유연성과 런타임의 중요성

이 OOP 비유는 Elixir의 비헤이비어와 콜백이 작동하는 방식과 정확히 일치합니다.

### 1. `@behaviour`와 `@callback`의 역할 (컴파일 타임 계약)

- `@behaviour`를 모듈에 선언하는 것은 "나는 이 비헤이비어의 계약을 따를 것이다"라고 컴파일러에 약속하는 것과 같습니다.
    
- 컴파일러는 이 약속을 보고, 해당 비헤이비어의 `@callback` 또는 `@optional_callbacks`로 정의된 모든 함수가 현재 모듈에 **정의되어 있는지** 확인합니다.
    
- 만약 `@callback`으로 정의된 **필수 콜백**이 구현되지 않았다면, 컴파일러는 **경고(Warning)**를 발생시킵니다. 이는 "네가 약속한 대로 모든 부분을 구현하지 않았으니, 런타임에 문제가 생길 수 있어!"라고 알려주는 부드러운 알림입니다. **하드 에러가 아닙니다.**
    
- `@optional_callbacks`로 정의된 콜백이 구현되지 않았다면, 컴파일러는 경고조차 발생시키지 않습니다.
    

### 2. 프레임워크의 런타임 논리 (실제 강제성)

Elixir 컴파일러는 코드의 형식적인 계약만 확인합니다. 즉, 어떤 콜백이 **실제로 애플리케이션 작동에 필수적인지**는 알지 못합니다. 이 정보는 해당 비헤이비어를 사용하는 **프레임워크(예: `GenServer` 자체 또는 `Phoenix.LiveView`)의 런타임 논리**에 내포되어 있습니다.

- **`render/1`의 경우**: `Phoenix.LiveView` 프레임워크는 특정 시점(예: 초기 마운트 후, 상태 변경 후)에 항상 `render/1` 콜백을 호출하도록 설계되어 있습니다. 이 콜백이 없으면 LiveView는 화면에 아무것도 그릴 수 없으므로, **런타임에 치명적인 오류(Crash)**가 발생합니다. 아무리 `@optional_callbacks`로 선언되었다 하더라도, 프레임워크가 이를 호출하려 할 때 함수가 없으면 애플리케이션은 중단됩니다.
    
- **`handle_info/2`의 경우**: `GenServer`나 `LiveView`의 `handle_info/2` 콜백은 해당 프로세스가 예상치 못한 메시지(자신에게 보내는 메시지 포함)를 받았을 때만 호출됩니다. 만약 해당 모듈이 그런 메시지를 받을 일이 없다면 `handle_info/2`를 구현하지 않아도 런타임 오류가 발생하지 않습니다. 이 콜백은 "선택적"인 것이죠.
    

## 결론: 개발자의 책임과 문서화의 중요성 💡

Elixir 비헤이비어와 콜백의 디자인은 **유연성**과 **개발자 경험**을 우선시한 결과입니다. 컴파일러는 경고를 통해 잠재적 문제를 알려주지만, 실제 애플리케이션의 동작과 필수적인 콜백의 구현 여부는 **프레임워크의 런타임 논리**와 **개발자의 책임**에 달려 있습니다.

따라서 Elixir 개발자로서 비헤이비어를 사용할 때는 다음과 같은 원칙을 기억해야 합니다:

1. **`@behaviour` 선언**: 모듈이 특정 비헤이비어를 따른다면 항상 `@behaviour`를 선언하여 컴파일러의 경고 시스템을 활용하세요.
    
2. **문서화 확인**: 각 콜백의 필수 여부는 해당 비헤이비어의 **공식 문서**를 통해 명확히 파악해야 합니다. `@callback`이나 `@optional_callbacks` 어트리뷰트만으로 런타임 필수 여부를 단정할 수는 없습니다.
    
3. **런타임 이해**: 프레임워크가 어떤 상황에서 어떤 콜백을 호출하는지에 대한 **런타임 컨텍스트**를 이해하는 것이 중요합니다.
    

이러한 이해를 바탕으로 Elixir의 유연성을 효과적으로 활용하고, 견고한 애플리케이션을 구축하시길 바랍니다!
